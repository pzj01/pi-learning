给循环装上刹车与兜底

第 1 课结尾我说「第 2 课讲怎么把两次请求折成循环」——你已经自己把 while (true) 写进 agent.ts 了。所以这一课不讲语法， 只做一件事：给你写的循环做一次体检，找出它在什么情况下会崩、在什么情况下停不下来。

1这一课要赢下什么

你的 run() 已经能把 5 + 3 这类问题跑通了。但它现在只在顺利的那条路上正确。这一课要让它在这四种情况下都体面收场——不崩、不死循环、有日志可查：

本节课的小胜利

四个破坏性实验，每个都先写下预测、再运行验证：

  1. 模型不调工具、直接回答
  2. 模型请求了一个你根本没实现的工具
  3. 工具执行时抛了异常
  4. 模型被 max_tokens 截断，finish_reason 不是你认识的那个值

四个都跑完之后，你的循环有明确的上界、有可解释的出口、错误有去处。

四个实验里，第 2 和第 4 个是本课的重头戏：它们暴露的是「协议债」，不是「语法错」。语法错当场就报，协议债会拖到下一轮请求才爆炸，而且报错信息完全不指向真正的病因。这是 agent 代码里最贵的一类 bug。

2先预测：你的循环有几个出口？

动手前，先预测

打开 mini-agent/src/agent.ts，只看你写的 run()，凭直觉回答：

  1. 这个 while (true) 一共有几个出口？（数 break 和 return）
  2. 如果某一轮模型既没有说话（content 为空）、也没有请求工具（tool_calls 为空），会发生什么？
  3. 接下来的第二次请求，它的 messages 和第一次请求相比有变化吗？
先自己数完再展开

1. 只有一个：if (choice.finish_reason === 'stop') { … break }。

2. 两个 if 都不成立 → 什么都不做，循环回到开头，用一模一样的 messages 再问一次模型。模型看到同样的输入，合理地再给出同样的输出 → 死循环。

3. 没有变化。第 2 题的后果和第 3 题是同一件事的两面：messages 不变 = 模型的输入不变 = 输出不变 = 无限循环。你的 API 额度会以每一轮一次请求的速度消失。

顺便留意：你的 const messages 写在模块顶层而不是 run() 里面。这意味着调用两次 run() 会共享同一份历史——第二次运行会「记得」第一次运行。现在不明显，等你做多轮对话时它就是 bug。第 7 节会顺手修掉。

「只有一个出口，而且它依赖 finish_reason 恰好等于 'stop'」——这就是本课要拆的第一个东西。

3finish_reason 有 6 个取值，你只认识 1 个

你的循环把 'stop' 当成唯一的「可以停」信号。那么问题来了：finish_reason 到底可能取哪些值？

以下是 DeepSeek 官方 API 文档里 finish_reason 的取值与释义（我从 create-chat-completion 逐字核对过）：

取值官方释义你的循环会怎样
'stop' 命中自然停止点或你给的 stop 序列 ✅ 正确退出
'tool_calls' 模型调用了工具 ✅ 继续下一轮（前提是工具都执行了，见第 4 节）
'length' 达到了请求里指定的 max_tokens 上限 ❌ 空转死循环
'content_filter' 内容因内容过滤器被省略 ❌ 空转死循环
'insufficient_system_resource' 因推理系统资源不足，请求被中断 ❌ 空转死循环
'aborted' 生成过程被中断 ❌ 空转死循环

六个取值里，只有两个是「正常业务」，另外四个全是故障。而你的循环遇到故障时的反应是——再问一遍。

为什么「白名单判停」是错的方向

你把「停」的条件写成了 finish_reason === 'stop'：只有命中我认识的那个值才停。这是白名单。白名单的隐含假设是「我已经穷举了所有取值」——而 finish_reason 的取值域由别人的服务器决定，你穷举不完。

正确的做法是把判据换到你自己能穷举的集合上。对你来说，「模型这一轮有没有要求我干活」只有两种可能：

const calls = message.tool_calls ?? []
if (calls.length === 0) // 没活干 → 停

这样无论 finish_reason 冒出第七、第八个取值，你都默认停下。意外值只会让你「少跑一轮」，不会让你「烧一整晚额度」。

TypeScript 在这里给了你一份借来的安全感

你本机 openai@7.32.0 的类型定义里，finish_reason 是这样写的：

// node_modules/openai/resources/chat/completions/completions.d.ts:261
finish_reason: 'stop' | 'length' | 'tool_calls' | 'content_filter' | 'function_call';

五个值，而且和 DeepSeek 对不上：SDK 里有 'function_call'（DeepSeek 没有），DeepSeek 有 'insufficient_system_resource' 和 'aborted'（SDK 没有）。

后果很具体——我实测过，你甚至写不出这个比较：

tsc 报错（本机实际复现）
const bad = finishReason === 'aborted'
// error TS2367: This comparison appears to be unintentional because the types
// '"content_filter" | "function_call" | "length" | "stop" | "tool_calls" | null'
// and '"aborted"' have no overlap.

类型系统拦住了你，但它拦错了方向：它不是在保护你，它是在告诉你「你拿到的类型描述的是 OpenAI 的形状，不是 DeepSeek 的真实形状」。对第三方 API 返回的枚举值，永远按运行时实际返回处理，不要按类型声明处理。

4不变式：tool_calls 的账必须平

这一节讲的 bug 藏在你已经写好的代码里，而且它是这份代码里最值得理解的一个缺陷。

先看协议给我们定的一条铁律：

协议不变式

只要一条携带 tool_calls 的 assistant 消息进了历史，它携带的每一个 id， 都必须在下一次请求之前收到恰好一条 tool 消息。

一条不多，一条不少。这是 Chat Completions API 强制的账目平衡。

你的代码是这样的：

mini-agent/src/agent.ts（现有代码，节选）
if (choice.message.tool_calls?.length) {
  messages.push(choice.message)              // ← 账已记上：assistant 要求调用 N 个工具
  for (const toolCall of choice.message.tool_calls) {
    if (toolCall.type === 'function' && tools.some(t => t.function.name === toolCall.function.name)) {
      //           ↑ 工具认识 → 执行并回一条 tool 消息
      ...
    }
    // 工具不认识 → 这个 toolCall 被整个跳过，什么都没回
  }
}

你写 tools.some(...) 这个检查的直觉完全正确——「模型让我调一个我不认识的工具，我不能瞎执行」。问题出在位置：你在 「执行」 这一步做了过滤，但账已经在上一行记下了。

于是历史里会出现这样一段：

被污染的历史
[
  { role: 'user',      content: '…' },
  { role: 'assistant', tool_calls: [{ id: 'call_A', … },
                                 { id: 'call_B', … }] },   // 要求调 2 个
  { role: 'tool',      tool_call_id: 'call_A', content: '8' },   // 只回了 1 个
]   // ← call_B 的账没平。下一次请求会被服务器拒绝。
这类 bug 为什么特别难查

报错现场和病因隔了一轮。出问题的那一轮你什么都察觉不到——程序没崩、日志正常、循环继续。你要等到下一轮请求才收到 HTTP 400，而错误信息只会说「assistant 消息里的 tool_calls 没有得到对应的 tool 响应」。

它一个字都不会提你的 if 语句。你会盯着发请求的那几行找半天，而真正的错留在上一轮的 for 循环里。这就是所谓「协议债」：借的时候没感觉，还的时候找不到人。

记住这一句，它能省掉一整类 bug

「跳过」不是错误处理，「回一条说明」才是。

工具不认识？不执行，但照样回一条 tool 消息，内容写「没有名为 X 的工具」。参数是坏 JSON？照样回一条，内容写「参数不是合法 JSON」。

这样做的第二个好处比第一个更重要：模型会读到这条消息，然后自己改主意——换个工具、换个参数、或者直接用自然语言告诉你它做不到。这就是 agent 从错误中自我修正的机制，而它的实现成本，仅仅是把错误当成一次正常的工具输出来发送。

5错误是给模型看的信息，不是给你看的异常

第 4 节说的是「账要平」，这一节说的是「账本上该写什么」。

你的 JSON.parse(toolCall.function.arguments) 没有 try/catch，tool.execute(...) 抛的异常也没人接。今天它们都会导致进程崩溃。修法不是「加个 try/catch 吞掉」，而是先分类：

失败的来源例子正确去向
模型的错 工具名写错、参数类型不对、缺必填字段、arguments 不是合法 JSON 作为 tool 消息的 content 回传给模型，让它自己修
工具的错（业务性） 查订单时订单不存在、除数为 0、文件格式不对 同上——回传，让模型决定怎么向下走
环境的错 网络断了、API key 失效、磁盘满、数据库连不上 往上抛，终止这次运行。回传给模型毫无意义
为什么环境错误不该回传

假设你的 API key 失效了。如果把「鉴权失败」当作工具结果发给模型，模型只会做它唯一会做的事：换个说法再调一次同一个工具。于是你的循环就变成一台「用模型调用量换一个已知事实」的机器——而这个事实（key 坏了）你本来就知道。

能自我修正的才回传，不能自我修正的立即失败。这条判断标准比具体的代码写法重要得多。

本节的最小实现，就落在下面这个函数里。注意它只有一个出口形态：无论成功失败，都返回一个值，不抛异常。

6最大步数：兜底刹车

前三节把「什么时候该停」讲清楚了，但还缺一层：即使所有判断都正确，循环仍然可能不结束。

因为 agent loop 是自我驱动的——每一轮的工具结果都会变成下一轮的输入，模型可以给自己安排新活。比如你给它加了搜索工具，它可能「搜一下 → 觉得不够 → 再搜一下 → 换个关键词再搜」。每一步都合规、每一次都有工具调用、finish_reason 一直是 'tool_calls'……它没有违反任何规则，它只是在绕圈。

这道刹车和前面那些修复不是一回事

第 3–5 节修的是 bug：有明确的病因，修掉就不再发生。最大步数防的不是 bug——它是承认「你无法事先证明循环一定终止」，于是给它一个硬上界。这类「不管对不对，先保证有界」的措施，工程上叫兜底（backstop / guardrail）。

兜底的价值在于：它把「无限」这个灾难性后果，降级成「跑满 8 轮」这个可接受的后果。代价只是你少了一次优雅的收场。

到达上限时，不要静默退出

撞上 MAX_STEPS 说明有东西不对劲，这是要大声报告的信号。别写成温和的 break——那会让你在日志里看到一次「正常结束」，然后花半小时想为什么答案不对。用 console.warn 明确说出「达到最大步数仍未结束，放弃」。

这在 agent 开发里是一条通用经验：「安静地降级」比「响亮地失败」危险得多。真实项目里，你会把这类信号接到日志或事件流上——那正是 Pi 那种规模的项目要专门做「事件系统」的原因之一（阶段 4 会看）。

① 在 calculator 之后插入

agent.ts · 新增
// 本地执行器认识的工具清单。发给模型的 tools 用的是同一个数组 —— 两者必须是同一份事实。
const tools = [calculator]

// 循环的上界。它防的不是 bug，而是「每一步判断都正确、模型却一直在绕圈」——
// 那种情况下烧掉的是你自己的 API 额度。
const MAX_STEPS = 8

/** 工具的产出：失败时不再抛异常，而是变成一段可以交给模型看的文本。 */
type ToolOutcome =
  | { ok: true, content: string }
  | { ok: false, error: string }

/**
 * 按工具名查找并执行。所有失败路径都在这里被转成返回值，
 * 以此保证一条协议不变式：模型每请求一个 tool_call，就一定能收到一条对应的 tool 消息。
 */
async function executeTool(name: string, rawArguments: string): Promise<ToolOutcome> {
  const tool = tools.find(t => t.function.name === name)
  if (!tool)
    return { ok: false, error: `没有名为「${name}」的工具` }

  let params: unknown
  try {
    // arguments 是 JSON 文本，而且模型并不保证它合法
    params = JSON.parse(rawArguments)
  }
  catch {
    return { ok: false, error: `参数不是合法 JSON：${rawArguments}` }
  }

  try {
    // 这个 as 是诚实的欠债：我们没做运行时校验，只是信任 schema。
    // 阶段 4 讲「工具系统」时会补上真正的参数校验。
    return { ok: true, content: String(await tool.execute(params as CalculatorParams)) }
  }
  catch (err) {
    return { ok: false, error: err instanceof Error ? err.message : String(err) }
  }
}

② 整段替换 run()

agent.ts · 替换 run()
export async function run(userMessage: string): Promise<string> {
  // 历史改成 run 的局部变量：模块级的 messages 会让两次 run() 共享历史
  const messages: ChatCompletionMessageParam[] = [
    { role: 'user', content: userMessage },
  ]

  for (let step = 1; step <= MAX_STEPS; step++) {
    const completion = await openai.chat.completions.create({
      messages,
      model: 'deepseek-flash',
      reasoning_effort: 'high',
      tool_choice: 'auto',
      stream: false,
      tools,
    })

    const { message, finish_reason: finishReason } = completion.choices[0]

    // 先入历史，且必须 push 整个对象 —— 手工挑字段重建会静悄悄丢字段（第 1 课第 7 节）
    messages.push(message)

    const calls = message.tool_calls ?? []

    // 唯一的停止判据：模型这一轮有没有要求我干活。
    // 不能用 finish_reason === 'stop' 判停 —— 它只是 6 个取值之一（第 3 节）。
    if (calls.length === 0) {
      console.log(`[step ${step}] 结束，finish_reason=${finishReason}`)
      return message.content ?? ''
    }

    console.log(`[step ${step}] 模型请求 ${calls.length} 个工具调用`)

    for (const call of calls) {
      let content: string

      if (call.type !== 'function') {
        // 非 function 型调用（SDK 里还有 custom 型）不在 tools 里，但一样得回一条 tool 消息
        content = `不支持的工具调用类型：${call.type}`
      }
      else {
        const outcome = await executeTool(call.function.name, call.function.arguments)
        content = outcome.ok ? outcome.content : `工具执行失败：${outcome.error}`
        console.log(`    ${outcome.ok ? '✓' : '✗'} ${call.function.name} → ${content}`)
      }

      messages.push({ role: 'tool', tool_call_id: call.id, content })
    }
  }

  console.warn(`[run] 达到最大步数 ${MAX_STEPS} 仍未结束，放弃。`)
  return ''
}

8四个破坏性实验

规则和第 1 课一样：每个实验先写下预测，再运行。改完记得改回来。

实验 A · 工具返回了一个「合法的垃圾值」

把 index.ts 里的问题改成 '请计算 5 除以 0'。

先预测：calculator 会抛错吗？会返回什么？模型会怎么回答？

展开

你的 execute 里 case 'divide': return a / b 没有任何校验。而 JavaScript 的除法不抛异常——5 / 0 是 Infinity。于是 String(Infinity) 得到 "Infinity"，它作为一次成功的工具结果发回模型。

有意思的地方在于第 1 课给出的 runCalculator 版本里，除零是 throw 的。两个版本哪一个是「对的」？严格说都对——但你要有意识地选：除零到底是「工具的调用失败」（该回传让模型知道），还是「合法的数学结果」（该照常返回）？没有校验的工具不会替你做这个选择，它会悄悄给你一个 Infinity。

如果模型没走工具、直接就回答了（它可能觉得「除零」是个常识问题、不需要算），换个说法再试一次，比如 '用计算器算一下 5 除以 0'。实验失败很多时候只是提示词没把模型推到你想要的那条路上。

这个实验真正在验证什么

从工具返回值到模型，中间没有任何一层会拦你。你的 String() 会把 NaN、Infinity、[object Object]、undefined 全都忠实地送给模型。如果模型没识破，你就会拿到一个看起来像模像样、实则荒谬的答案。工具该自己校验自己的输入和输出——这是工具设计的第一条纪律。

实验 B · 模型要调的工具，我没有实现

这个实验分两步：先用新代码看「正确的行为是什么样」，再把修复拆掉，看旧行为怎么炸。

第一步。把 executeTool 里的查找改成：

const tool = tools.find(() => false)  // 实验 B：假装这个工具名我不认识

find(() => false) 永远返回 undefined，类型也完全合法——所以 tsc 不会拦你。

先预测：这一次会报 400 吗？程序会崩吗？模型会怎么回答？

展开

不会报 400，也不会崩——这正是修复的价值所在。你会看到：

[step 1] 模型请求 1 个工具调用
    ✗ calculator → 工具执行失败：没有名为「calculator」的工具
[step 2] 结束，finish_reason=stop
最终回答： 我无法使用计算器来算，但 5 + 3 = 8。

注意最后那句回答——模型读懂了「没有这个工具」，然后自己绕过去了。这一步没有写任何特殊逻辑，只是因为错误走了「正常的工具结果」这条路。

第二步。把修复拆掉，看看没有它会发生什么。把 run() 里那个 else 分支换成旧写法——「不认识的工具就跳过，什么也不回」：

for (const call of calls) {
  if (call.type !== 'function') continue
  const tool = tools.find(t => t.function.name === call.function.name)
  if (!tool) continue          // ← 实验 B 第二步：只跳过，不回消息
  const outcome = await executeTool(call.function.name, call.function.arguments)
  messages.push({ role: 'tool', tool_call_id: call.id, content: outcome.ok ? outcome.content : outcome.error })
}

再预测一次：这次错误会在第几轮出现？是本地报错还是服务器报错？报错信息会提到 continue 吗？

展开

第 1 轮平静地过去了——没有日志、没有异常，只有那个 continue 悄悄执行。然后第 2 轮请求撞上 HTTP 400，大意是「assistant 的 tool_calls 没有得到对应的 tool 消息」。

这就是第 4 节的现场演示：

  • 病因在第 1 轮的 continue，报错在第 2 轮的网络请求。
  • 报错信息一个字都不会提 continue——它只会描述「历史里少了一条 tool 消息」这个现象。
  • 你会盯着发请求的那几行找很久，而真正的错留在上一轮的循环里。

对比第一步和第二步：两段代码只差一行，一分钱都没多花，但一段能自愈、一段直接崩。这就是「跳过」和「回一条说明」的全部区别。

实验 C · 工具自己抛错

在 calculator.execute() 的第一行加：

throw new Error('数据库连接失败')  // 实验 C

先预测两件事：(a) 程序会崩吗？(b) 模型读到「工具执行失败：数据库连接失败」之后，会说什么？

展开

(a) 不会崩。错误在 executeTool 里被转成了返回值，然后变成一条正常的 tool 消息。循环继续。

(b) 这才是值得盯着看的部分，而且它不一定是你期望的结果。模型可能老实说「我无法计算，因为工具出错了」——也可能直接心算给你一个答案，因为 5 + 3 它本来就会算。如果它选了后者，你就看到了一个真实且重要的现象：模型会在工具失败时「假装」工具成功了。这就是为什么工具结果需要可信来源，为什么生产系统会在这里加校验——也是阶段 2「错误处理」之后值得单独记一笔的观察。

还有一种可能：它再调一次同一个工具。工具又抛错，于是循环一直走到 MAX_STEPS 才停下——这是 MAX_STEPS 价值的第二次现场演示（第一次在实验 D）。看到这个结果不要觉得是 bug：模型没有记忆「我刚刚试过并且失败了」之外的判断力，它只能看到历史里堆着几条「工具执行失败」。真实系统在这里会加「同一个工具连续失败 N 次就不再重试」的策略——那属于阶段 2 的停止条件。

实验 C 和实验 A 是同一枚硬币

实验 A：工具成功返回了垃圾，模型照单全收。
实验 C：工具失败了，模型可能照样给你一个答案。
合起来是一条结论：在 agent 里，模型的输出是否可信，取决于你是否替它守住了工具这一侧。模型没有能力分辨「这是真数据」和「这是它自己编的」——这个判断只能由你的代码来做。

实验 D · 让 finish_reason 变成一个你不认识的值

这个实验分两步，顺序不能颠倒——先装刹车，再用它试刹车。

  1. 在请求参数里加一行 max_tokens: 1。这会让模型几乎必然被截断，finish_reason 变成 'length'。
  2. 把停止判据临时改回白名单写法——只改条件，其余一行都不要动： 
    if (finishReason === 'stop') {   // 实验 D：临时改回「只有 stop 才停」
  console.log(`[step ${step}] 结束，finish_reason=${finishReason}`)
  return message.content ?? ''
}
    这时 finish_reason 是 'length'，条件不成立，于是继续往下走；而 calls 是空的，下面那个 for 循环什么都不做——一轮里什么都没发生，循环回到开头。

先预测：程序会做什么？跑完之后，把两次的输出对照一下：

对照观察
// 判据 = finishReason === 'stop'（白名单）
[run] 达到最大步数 8 仍未结束，放弃。   ← 注意：中间一步日志都没有

// 判据 = calls.length === 0（你能穷举的集合）
[step 1] 结束，finish_reason=length    ← 第 1 轮就干净退出

第一种输出里值得注意的不是那行 warn，而是它前面的空白：八轮请求，一条日志都没留下。原因是旧的判据只在命中 'stop' 时才 console.log，没命中时它就悄无声息地转一圈——转完什么都不说。所以你的第一反应会是「程序卡住了」，而不是「它空转了八次」。

展开：这两次输出的差别

第一次运行里，八轮请求发的是完全一样的 messages，拿到的是完全一样的回答（content 空、finish_reason 一直是 'length'），条件始终不成立，于是永远原地打转。

这一次是 MAX_STEPS 救了场：如果没有它，这段代码会以每秒几次请求的速度，一直跑到你手动 Ctrl-C 或者额度耗尽。这就是第 6 节说的「把无限降级成有限」——它没有让程序变正确，它只是让错误的代价变得可承受。

第二次运行里，你第 1 轮就退出了，日志明确写着 finish_reason=length——它不假装成功，它把「我是被截断的」这个事实交给你处理。

做完四个实验，回 notes/ 记一笔

按你 ROADMAP 里的模板，重点记三样东西：① 我预测了什么 ② 实际发生了什么 ③ 差在哪里。第 ③ 项最有价值——第 1 课你记的三条坑（arguments 是字符串、靠 tool_call_id 配对、历史要完整）记的正是「和直觉不一样的地方」。

这一课我建议你补的，是「报错现场和病因隔了一轮」那条。它比任何一条语法规则都更常救你。

9检查理解

合上代码，凭记忆回答。

检查 1 / 3 模型这一轮返回：finish_reason: 'length'、content: ''、tool_calls 为 undefined。你的循环应该怎么做？

content 为空说明这轮没东西可给用户，tool_calls 为空说明模型也没要求你干活——这一轮没有下一步可走，循环必须结束。而 finish_reason 的价值就在这里：它告诉你结束的原因，让你能区分「模型说完了」和「模型被打断了」。后者应该按失败处理（重试、告知用户、或截断后重发），而不是伪装成一次成功。

检查 2 / 3 模型在一次回复里请求了 2 个工具调用：calculator（你实现了）和 get_weather（你没有实现）。正确做法是？

协议要求的是每个 tool_call_id 都有一条回应，而不是「有返回值的才回应」。所以：「跳过」不是错误处理，「回一条说明」才是。而且这条说明不是白写的——模型会读到「没有 get_weather 这个工具」，然后自己改用别的方式回答。这就是 agent 自我修正的入口。

检查 3 / 3 工具在执行中抛出了Error('API key 无效')。这个错误最适合怎么处理？

判据是：这个错误，模型能不能自己修正？参数写错、工具名不对、格式不合法——能，回传。网络断了、key 失效、磁盘满——不能，立即失败。把不能自我修正的问题交给模型，只会得到一台用 API 调用量换取已知事实的机器。
（顺带一提：Error('数据库连接失败') 就属于边界情况——回传它并不算错，但你要有意识地选，而不是因为「所有错误都统一回传」这个规矩。）

顺便更新第 1 课的一个不确定项

关于 thinking 模式

第 1 课我标注过：「reasoning_effort: 'high' 是否真的让 deepseek-flash 进入 thinking 模式，我没有实测」。这次查 DeepSeek 官方文档时我发现了上次漏掉的一条：文档里有一个显式开关——

// Node SDK 里这样写（官方示例，与 reasoning_effort 并列）
const completion = await openai.chat.completions.create({
  model: 'deepseek-flash',
  messages,
  thinking: { type: 'enabled' },
  reasoning_effort: 'high',
})

也就是说：「要不要进入 thinking 模式」是可显式控制的，不用靠猜。另外文档里还有一句：「From DeepSeek-V3.2, the API supports tool use in the thinking mode.」

但仍然未实测：你这套代码走的是 reasoning_effort 而没有 thinking 开关，是否实际进了 thinking 模式、从而是否触发 reasoning_content 回传规则，我依然没有验证过（要动用你的 key）。这条留给以后需要开 thinking 时再处理——第 1 课那条规则届时会回来。

本课的事实边界

我在本机实测过的：你现有的 agent.ts 类型检查是干净的（tsc --noEmit，加了 skipLibCheck 过滤 node_modules 噪音）；第 7 节的新代码同样类型检查干净；finish_reason === 'aborted' 会触发 TS2367（第 3 节截图是真跑出来的）；pnpm exec tsc --noEmit 在你项目里会刷满 node_modules 的错误。

逐字核对过官方文档的：finish_reason 的 6 个取值与释义、strict beta 模式、Chat Completion API 不支持中途插入 tool call、thinking 开关。

属于我的预测、需要你用实验验证的：实验 B 里悬空 tool_call 导致的 HTTP 400（第 1 课的速查表里也列了这条，但我没亲眼看它报出来）；实验 D 里 max_tokens: 1 是否稳定产生 'length'；实验 C 里模型面对工具失败的实际反应。
