1这一课要赢下什么

先说你跑完会得到什么：

本节课的小胜利

6 个测试全绿，不联网、不花 API 额度，甚至不需要 DEEPSEEK_API_KEY。而且它们覆盖的正是你之前最难受的几件事：

  1. 模型直接回答 → 一轮就停
  2. 模型调用工具 → 第二轮请求里的历史角色、顺序、tool_call_id 全部正确
  3. 模型请求不存在的工具 → 账照样平
  4. 工具参数是坏 JSON → 进程不崩
  5. 模型一直要求干活 → 恰好停在 maxTurns
  6. finish_reason 是个没见过的值且没有工具调用 → 立即停

全部跑完，用时不到 0.3 秒。

第 2 课的实验 B 和 D 有个共同点：为了制造一个分支，你得改生产代码（假装工具不存在、临时改回白名单判停）。实验 C 更麻烦——模型每次的反应都不一样。测试要解决的，就是这种「场景能描述、却没法稳定复现」的窘境。

第 2 课的四个实验如果你还没跑完，不影响这一课。其中 B、D 两个场景，这一课会用测试确定性地重建出来；C 里「模型面对工具失败会怎么回答」仍然只有真模型能告诉你。

2为什么你之前「测不了」

先看你现在 run() 开头的几行：

mini-agent/src/agent.ts（现有代码，节选）
export const openai = new OpenAI({
  apiKey: process.env.DEEPSEEK_API_KEY,
  baseURL: process.env.DEEPSEEK_API_BASE,
})

export async function run() {
  const context: ChatCompletionCreateParamsNonStreaming = {
    messages: [{ role: 'user', content: '请计算 1500 除以 3' }],
    // …
  }

  const completion = await openai.chat.completions.create(context)

这段代码把三样东西焊死在 run() 里了：

输入

用户消息写死在函数体里。想测「未知工具」得先改代码。

模型

run() 直接引用模块级的 openai。想让它返回预设响应，只能 mock 整个模块。

凭据

new OpenAI() 在模块加载时就会校验 key。测试文件只要 import 它，没有 key 就直接崩。

所以问题不是「缺一个测试框架」。缺的是接缝（seam）——一个允许你在测试时把「真模型」换成「假模型」的地方。

这一课真正要记住的一句话

可测试性不是测试文件带来的，是生产代码的依赖边界带来的。

如果一个函数内部直接 new 了外部资源、直接读了全局配置、直接把结果 console.log 出去，那么你写再多的测试文件也只能绕着它走。改法不是「加 mock」，而是把这些东西从函数内部挪到参数列表上。

3依赖注入：本质就是「多一个参数」

「依赖注入」（dependency injection）听起来像框架术语，但在这个项目里，它就是一个默认参数：

export async function run(
  userMessage: string,
  options: {
    model?: ChatModel      // 生产环境不传，用真模型
    maxTurns?: number
  } = {},
): Promise<string>

其中 ChatModel 是我们自己定义的一个窄接口——只描述 run() 真正需要模型做的那一件事：

export interface ChatModel {
  create: (params: ChatCompletionCreateParamsNonStreaming) => Promise<{ choices: DeepseekChoice[] }>
}

为什么是「窄」接口？因为如果直接要求一个完整的 OpenAI 类型，测试里的 fake 就得伪造 chat、completions、create、stream 一大堆用不到的东西。接口越窄，替换成本越低，测试越容易写。

TypeScript 是结构化类型：真 client 和 fake 只要形状对得上，就能互相替换，不需要继承或注册。

为什么不用「mock 整个 openai 模块」

你当然可以在测试里写 vi.mock('openai') 之类的东西。但它有三个问题：

  • 隐式：测试是否生效取决于模块路径和加载顺序，读代码看不出来。
  • 易碎：改一下 import 的路径，mock 可能悄悄失效。
  • 没有类型保护：fake 写错字段，编译器不会帮你。

把 model 做成参数以后，替换发生在明面上：调用 run(..., { model: fake }) 的人一眼就能看到。这就是为什么依赖注入比模块 mock 更值得学——它不是测试技巧，是设计。

4一个必须先解决的坑：模块加载就要 key

改 run() 之前，还有一个隐藏依赖。你现在的代码在模块顶层创建 client：

export const openai = new OpenAI({ apiKey: process.env.DEEPSEEK_API_KEY, … })

我实测过：没有 DEEPSEEK_API_KEY / OPENAI_API_KEY 时，这一行会直接抛错——

本机实际输出
construct throws: Missing credentials. Please pass an `apiKey`, `workloadIdentity`,
`adminAPIKey`, or set the `OPENAI_API_KEY` or `OPENAI_ADMIN_KEY` environment variable.

也就是说：测试文件只要 import { run } from './agent'，测试还没开始就已经失败了。这不是测试写得不对，是 client 创建得太早。

修法是把 client 变成懒加载——第一次真正要请求模型时才创建：

let client: OpenAI | undefined
function getClient(): OpenAI {
  client ??= new OpenAI({
    apiKey: process.env.DEEPSEEK_API_KEY,
    baseURL: process.env.DEEPSEEK_API_BASE,
  })
  return client
}

这样：真实运行时行为不变（第一次调用仍然会用你的 key），但测试进程可以完整加载模块、跑完全部 fake 测试，一次都不碰 key。这条我实测过——把两个环境变量都 unset，6 个测试照样全绿。

5动手 ①：改造 agent.ts

整份文件替换成下面这样。前三段（Executable 那些）不在这里，它们在 tool.ts 里，不需要动。

mini-agent/src/agent.ts · 完整替换
import type {
  ChatCompletionCreateParamsNonStreaming,
  ChatCompletionMessageToolCall,
  ChatCompletionToolMessageParam,
  DeepseekChoice,
} from 'openai/resources/chat/completions'
import process from 'node:process'
import { OpenAI } from 'openai'
import logger from './log'
import { executeTool, tools } from './tool'
import 'dotenv/config'

const MAX_TURNS = 8

/**
 * run() 对模型的全部要求：拿到请求参数，返回若干条 choice。
 * 接口故意收窄 —— 测试里的 fake 只要能返回 choices，不需要伪造整个 ChatCompletion。
 */
export interface ChatModel {
  create: (params: ChatCompletionCreateParamsNonStreaming) => Promise<{ choices: DeepseekChoice[] }>
}

// 懒加载：模块被 import 时不校验 key，只有真的请求模型时才创建 client。
// 否则测试文件只要 import agent.ts 就会因为缺少 API key 崩溃。
let client: OpenAI | undefined
function getClient(): OpenAI {
  client ??= new OpenAI({
    apiKey: process.env.DEEPSEEK_API_KEY,
    baseURL: process.env.DEEPSEEK_API_BASE,
  })
  return client
}

// SDK 的类型描述的是 OpenAI 的 finish_reason 形状，和 DeepSeek 对不上；
// 这层 adapter 把类型谎言收敛到一行，run() 内部只面对 DeepseekChoice。
const deepseek: ChatModel = {
  create: async params =>
    await getClient().chat.completions.create(params) as unknown as { choices: DeepseekChoice[] },
}

export interface RunOptions {
  model?: ChatModel
  maxTurns?: number
}

export async function run(userMessage: string, options: RunOptions = {}): Promise<string> {
  const { model = deepseek, maxTurns = MAX_TURNS } = options

  const context: ChatCompletionCreateParamsNonStreaming = {
    // 上下文消息列表，包含用户输入和助手的回复
    messages: [
      {
        role: 'user',
        content: userMessage,
      },
    ],
    model: 'deepseek-flash',
    reasoning_effort: 'high',
    tool_choice: 'auto',
    stream: false,
    tools,
  }

  logger.setup(context)

  // agent loop
  for (let turn = 1; turn <= maxTurns; turn++) {
    try {
      const completion = await model.create(context)
      const { message, finish_reason } = completion.choices[0]

      // 先把 assistant 消息原样放进历史，再执行工具：协议账目先记上
      context.messages.push(message)

      const toolCalls = message.tool_calls ?? []

      // 判据：模型这一轮有没有要求我干活。
      // 不用 finish_reason 白名单判停 —— 它的取值域由服务器决定，穷举不完。
      if (toolCalls.length === 0) {
        logger.finish(finish_reason)
        return message.content ?? ''
      }

      for (const toolCall of toolCalls) {
        logger.tool(toolCall)
        context.messages.push(await toToolMessage(toolCall))
      }
    }
    catch (error) {
      logger.error(error as Error)
      throw error
    }
  }

  logger.error(`Max turns reached (${maxTurns})`)
  return ''
}

/**
 * 把一次工具调用变成一条 tool 消息。
 * 无论成功失败都返回一条，保证每个 tool_call_id 的账都是平的。
 */
async function toToolMessage(toolCall: ChatCompletionMessageToolCall): Promise<ChatCompletionToolMessageParam> {
  const result = await executeTool(toolCall)
  return {
    role: 'tool',
    tool_call_id: toolCall.id,
    content: result.ok ? result.content : `Error executing tool: ${result.error.message}`,
  }
}

改动与理由：

改动为什么
run() 接收 userMessage 输入从函数体里挪出来，测试才能构造任意场景
模型通过 options.model 注入，默认 deepseek 生产调用保持不变，测试可以塞 fake
new OpenAI() 改成懒加载 getClient() 没有 key 也能 import 模块；这是测试能跑的前提
停止判据改成 toolCalls.length === 0 第 2 课的核心结论：判据要建在你能穷举的集合上
抽出一个 toToolMessage() 「账要平」这件事只有一个实现点，测试也只需要盯这一处
两个出口都返回 string 把隐式契约（可能返回 undefined）变成显式契约，测试才好断言
我注意到你保留了 finish_reason 白名单

你现在的停止分支是 finish_reason === 'stop' || 'length' || …，除了 'tool_calls'，文档里的另外五个值都列进去了。但第 2 课说过：白名单的假设是「我已经穷举了所有取值」，而取值域由服务器决定。如果哪天多出第七个值、且这一轮没有 tool_calls，你的循环会空转到 MAX_TURNS。

新代码把判据换成 toolCalls.length === 0 后，未知值只会让你少跑一轮，不会让你空转八轮。而 finish_reason 仍然保留——它现在是「报告停止原因」的信息，不再是「决定是否停止」的开关。第 6 节最后一个测试专门守这条。

6动手 ②：写测试

测试框架的选择先交代清楚：这一课用 Node 内置的 node:test，不装 vitest。

为什么不用 vitest

你现在需要的是「跑几个纯函数测试」，node:test 已经够了，而且：

  • 零新增依赖：项目里已经有 tsx，直接 tsx --test 就能跑 TypeScript。
  • 不用额外配置 vitest.config.ts，不用处理 DOM、watch、覆盖率这些你暂时用不到的东西。

什么时候该换？当你开始需要 watch 模式、更丰富的 mock API、覆盖率报告或 UI 时，再引入 vitest 不迟。到那时，这一课的测试几乎可以原样迁移——test / assert 的形状是相通的。

代价：antfu 的 ESLint 配置默认假设你用 vitest，会报 test/no-import-node-test。测试文件顶部加一行带原因的禁用注释即可（下面代码里有）。

新建 mini-agent/src/agent.test.ts：

mini-agent/src/agent.test.ts
import type {
  ChatCompletionCreateParamsNonStreaming,
  ChatCompletionMessage,
  ChatCompletionMessageToolCall,
  ChatCompletionToolMessageParam,
  DeepseekChoice,
} from 'openai/resources/chat/completions'
import type { ChatModel } from './agent'
import assert from 'node:assert/strict'
// eslint-disable-next-line test/no-import-node-test -- 刻意选零依赖的 Node 内置 runner，不引入 vitest
import { test } from 'node:test'
import { run } from './agent'

/** 造一条 assistant 回复。finish_reason 必填，其余字段按需覆盖。 */
function reply(finishReason: DeepseekChoice['finish_reason'], message: Partial<ChatCompletionMessage> = {}): DeepseekChoice {
  return {
    index: 0,
    logprobs: null,
    finish_reason: finishReason,
    message: { role: 'assistant', content: null, refusal: null, ...message } as ChatCompletionMessage,
  }
}

/** 造一次工具调用。rawArguments 用来模拟模型给出的坏 JSON。 */
function toolCall(name: string, rawArguments: string, id = 'call_1'): ChatCompletionMessageToolCall {
  return {
    id,
    type: 'function',
    function: { name, arguments: rawArguments },
  }
}

interface FakeModel extends ChatModel {
  calls: ChatCompletionCreateParamsNonStreaming[]
}

/**
 * 按顺序吐出预先写好的响应，并记录每次请求的参数。
 * 注意记录时只深拷贝 messages：params.tools 里带着 execute 函数，
 * structuredClone 整个对象会抛 DataCloneError。
 */
function fakeModel(...responses: DeepseekChoice[]): FakeModel {
  const calls: ChatCompletionCreateParamsNonStreaming[] = []
  return {
    calls,
    async create(params) {
      calls.push({ ...params, messages: structuredClone(params.messages) })
      const response = responses.shift()
      if (!response)
        throw new Error('fake model 没有更多响应了')
      return { choices: [response] }
    },
  }
}

test('模型直接回答：一次请求后停止', async () => {
  const model = fakeModel(reply('stop', { content: '你好' }))

  const answer = await run('打个招呼', { model })

  assert.equal(answer, '你好')
  assert.equal(model.calls.length, 1)
  assert.deepEqual(model.calls[0].messages, [{ role: 'user', content: '打个招呼' }])
})

test('一次工具调用：第二轮历史里 tool 消息与 tool_call_id 对上', async () => {
  const model = fakeModel(
    reply('tool_calls', {
      tool_calls: [toolCall('calculator', '{"operation":"add","a":2,"b":3}')],
    }),
    reply('stop', { content: '结果是 5' }),
  )

  const answer = await run('2 + 3 等于几', { model })

  assert.equal(answer, '结果是 5')
  assert.equal(model.calls.length, 2)

  // 第二轮请求发出去时，模型必须能看到 user → assistant(tool_calls) → tool 三段
  const history = model.calls[1].messages
  assert.equal(history.length, 3)
  assert.equal(history[1].role, 'assistant')

  const toolMessage = history[2] as ChatCompletionToolMessageParam
  assert.equal(toolMessage.role, 'tool')
  assert.equal(toolMessage.tool_call_id, 'call_1')
  assert.equal(toolMessage.content, '5')
})

test('未知工具：回一条说明，而不是跳过', async () => {
  const model = fakeModel(
    reply('tool_calls', {
      tool_calls: [toolCall('get_weather', '{"city":"北京"}')],
    }),
    reply('stop', { content: '我没有天气工具' }),
  )

  await run('明天北京天气', { model })

  const history = model.calls[1].messages
  const toolMessage = history[2] as ChatCompletionToolMessageParam
  assert.equal(history.length, 3, '悬空的 tool_call 会让账不平')
  assert.equal(toolMessage.tool_call_id, 'call_1')
  assert.match(String(toolMessage.content), /Tool not found/)
})

test('工具参数不是合法 JSON：错误变成 tool 消息，进程不崩', async () => {
  const model = fakeModel(
    reply('tool_calls', {
      tool_calls: [toolCall('calculator', '{not json')],
    }),
    reply('stop', { content: '参数格式不对，我再试一次' }),
  )

  const answer = await run('算一下', { model })

  assert.equal(answer, '参数格式不对，我再试一次')
  const toolMessage = model.calls[1].messages[2] as ChatCompletionToolMessageParam
  assert.match(String(toolMessage.content), /Invalid tool call arguments/)
})

test('达到 maxTurns：请求次数有上界', async () => {
  const alwaysCallsTool = () =>
    reply('tool_calls', {
      tool_calls: [toolCall('calculator', '{"operation":"add","a":1,"b":1}')],
    })
  const model = fakeModel(alwaysCallsTool(), alwaysCallsTool(), alwaysCallsTool())

  const answer = await run('一直算', { model, maxTurns: 3 })

  assert.equal(model.calls.length, 3)
  assert.equal(answer, '')
})

test('没见过的 finish_reason 且没有工具调用：按停止处理', async () => {
  // 模拟服务器未来新增了一个取值；判据必须建在「有没有 tool_calls」上
  const model = fakeModel(reply('something_new' as DeepseekChoice['finish_reason'], { content: '' }))

  const answer = await run('说点什么', { model })

  assert.equal(model.calls.length, 1)
  assert.equal(answer, '')
})

fake model 的两个设计点

① 它同时是「响应队列」和「录音机」。队列负责让模型按剧本说话，录音机负责让你事后检查「run() 到底把什么发给了模型」。很多测试只断言最终答案，那等于只看了考试的最后一题；断言请求历史，才是在确认完整执行顺序——这正是 ROADMAP 里那条 checkbox 的本意。

② 记录时必须深拷贝 messages。这是这一课最容易踩的坑：context.messages 是同一个可变数组，第二轮、第三轮还会继续 push。如果你只写 calls.push(params)，那么所有记录都指向同一个数组——测试跑完后去看第一轮的记录，看到的却是最终状态。录像带必须当场拷贝，事后再看已经晚了。

但不能 structuredClone(params) 整个对象

params.tools 里的 calculator 带着 execute 函数，而 structuredClone 不能克隆函数。我实测过，会抛：

DataCloneError - execute() {} could not be cloned.

所以只克隆你真正要断言的 messages：{ ...params, messages: structuredClone(params.messages) }。

每个测试在守什么

测试它守的规则
模型直接回答没有工具调用 → 一轮结束，请求里只有一条 user 消息
一次工具调用协议不变式：角色顺序正确，tool_call_id 对得上，工具结果真的回传了
未知工具「跳过」不是错误处理；历史长度必须是 3，账要平
坏 JSON解析失败变成一条 tool 消息，而不是异常冒泡
达到 maxTurns兜底刹车真的生效，请求次数恰好等于上界
未知 finish_reason停止判据不依赖服务器的枚举值

8选做实验：让测试替你抓 bug

下面三个实验都不联网。先写测试、看它失败，再改代码。

实验 A · 除零

给 agent.test.ts 加一个测试：让模型请求 calculator 执行 5 ÷ 0，断言第二轮历史里的 tool 消息包含 Division by zero，并且 run() 还能拿到模型的最终回答。

展开参考实现 
test('除零：工具错误回传给模型', async () => {
  const model = fakeModel(
    reply('tool_calls', {
      tool_calls: [toolCall('calculator', '{"operation":"divide","a":5,"b":0}')],
    }),
    reply('stop', { content: '不能除以 0' }),
  )

  const answer = await run('5 除以 0', { model })

  assert.equal(answer, '不能除以 0')
  const toolMessage = model.calls[1].messages[2] as ChatCompletionToolMessageParam
  assert.match(String(toolMessage.content), /Division by zero/)
})

这个测试直接验证了第 2 课实验 A 的结论：工具的错误有没有变成模型能读到的信息。

实验 B · 一次回复里两个工具调用

让模型一次返回两个 tool_calls（比如两次 calculator，id 分别是 call_1 / call_2），断言第二轮历史长度是 4，并且两条 tool 消息的 tool_call_id 分别对上。

展开提示

历史应该是：user → assistant（带 2 个 tool_calls）→ tool(call_1) → tool(call_2)。

这个测试守的是第 2 课那条不变式的复数形式：不是「至少回一条」，而是每一个 id 恰好一条。

实验 C · 故意把账弄不平

把 toToolMessage 的返回值从 context.messages.push(...) 改成不 push（或者把 for 循环提前 break），再跑测试。

先预测：哪个测试会红？它会报「HTTP 400」吗？

展开

红的会是「一次工具调用」和「未知工具」两个测试，失败信息是 history.length 不等于 3——本地断言当场就抓到了。

这正是测试相对真实请求的价值：第 2 课里同样的 bug 要等到下一轮真实 HTTP 请求才暴露，而且报错信息不指向病因；在这里，它在 0.3 毫秒内失败，并直接告诉你「历史里少了一条消息」。把协议不变式写成断言，等于给「隔一轮才爆炸的 bug」装了一个即时警报器。

9检查理解

合上代码，凭记忆回答。

检查 1 / 3 为什么把模型做成 run() 的参数，而不是在测试里 mock 整个 openai 模块？

依赖注入把「用哪个模型」从代码内部挪到了调用处：run(msg, { model: fake }) 一眼可见，fake 写错字段编译器会报错。模块 mock 依赖模块路径和加载顺序，测试是否真的替换成功，读代码看不出来。

检查 2 / 3 fake model 记录请求时，为什么必须用 structuredClone(params.messages)，而不是直接 calls.push(params)？

run() 全程复用同一个 context.messages 数组。假模型如果只存对象引用，等测试结束时再去看 calls[0]，看到的是被后续轮次追加过的「最终历史」。录音必须当场拷贝。

检查 3 / 3 下面哪条断言，最能确认「工具调用的完整执行顺序」是正确的？

最终答案和「没崩」都太粗：一个错误的协议历史也可能碰巧得到正确答案。真正要守的是发给模型的那份历史——user → assistant → tool 的顺序、每个 tool_call_id 都有回音、工具结果内容正确。这些断言在真实请求里要等到下一轮 HTTP 400 才会暴露。

下一课：多轮对话

你现在有了一个可测试的一问一答 agent：每次 run() 都从一条 user 消息开始，结束就丢掉历史。下一课把它变成会话：

  • 历史从哪来、存在哪、什么时候该丢；
  • 第二次提问时，哪些旧消息必须保留（回顾第 1 课的协议不变式）；
  • 用这一课学到的 fake model，测试「连续两问」时历史是否按预期累积。

你会发现这一课投入的测试基础设施，在下一课立刻回本——会话状态最容易出的 bug，恰恰是「历史多了/少了/顺序错了」，而这些都能用 calls[1].messages 断言出来。
