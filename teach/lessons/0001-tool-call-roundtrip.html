工具调用的完整往返

你的 calculator tool schema 已经写好了，但模型的手还没伸出来。 这一课只解决一件事：让模型请求一次工具调用，你执行它，再把结果交回去，直到模型开口说出最终答案。

⏱ 约 45 分钟 🎯 对应 ROADMAP 阶段 1 前五项 🔧 需要动手改代码

1这一课要赢下什么

一个具体的、可验证的胜利：

本节课的小胜利

在终端里跑通一次完整的工具调用往返，看到程序打印出的最终回答是 5 + 3 = 8，并且你能指着屏幕说清每条消息是谁产生的、为什么必须在那里。

我们故意不写 while 循环。原因是：循环本身只有三行，是个语法问题；真正难的是消息协议——第二次请求里必须塞进什么、顺序是什么、字段叫什么。手工把一次往返走通，循环就变成了显而易见的事。反过来先写循环，你会被"为什么报错说找不到 tool call"卡住很久。

2先预测，再看答案

研究一再表明：先猜、再验证的学习效果远好于直接阅读。别跳过这一步——花两分钟在纸上或心里写下你的答案。

动手前，先预测

你要发一条 "请计算 5 + 3 的结果" 给模型，并附上 tools: [calculatorTool]。凭直觉回答：

  1. 模型返回的 message.content 会是什么？是 "8" 吗？
  2. 模型自己算得出来 5 + 3 吗？它需要你的 calculator 吗？
  3. 如果模型要调工具，它是直接帮你执行了，还是只告诉你"我想调"？
做完第 3 节再展开答案（现在展开会损失一次检索练习）

1. 大概率是 null。当模型决定调用工具时，它的意图放在 tool_calls 字段里，content 往往是空的。

2. 它算得出来——但这里的目标不是"能不能算"，而是让你看清协议。工具的价值在于模型算不准、或根本不知道的事（查数据库、调 API、读文件）。

3. 只告诉你"我想调"。模型在 API 里没有任何执行能力，它只是输出一段结构化的 JSON，表明"请帮我调用 calculator，参数是这些"。真正的执行发生在你的代码里。这是整门课最重要的一个认知。

3知识：一次往返 = 两次请求 + 四条消息

模型不能执行工具，但它可以"填一张申请表"。你的程序读完申请表，自己干活，再把回执贴回去，模型才能继续往下说。

抽象成消息列表，一次完整的 tool call 是这样的：

#谁产生role关键字段内容示例
1你user content请计算 5 + 3 的结果
2模型assistant tool_calls我要调 calculator，参数 {"operation":"add","a":5,"b":3}
3你的代码tool tool_call_id + contentcall_abc 的结果是 8
4模型assistant content5 + 3 = 8

而这四条消息是分两次请求发出去的：

  1. 请求 1 [msg 1]
  2. 响应 1 [msg 2]
  3. 本地执行工具
  4. 请求 2 [msg 1,2,3]
  5. 响应 2 [msg 4]

三个必须记住的点，全部来自协议本身：

① arguments 是字符串

你拿到手的 call.function.arguments 是一段 JSON 文本，不是对象。想用必须先 JSON.parse()。这是初学者最常踩的坑。

② 靠 tool_call_id 配对

模型可能一次请求多个工具。结果消息必须带上 tool_call_id，模型才知道这条结果是对哪次调用的回答。ID 对不上就会报错。

③ 历史要完整

第二次请求必须把第 2 条 assistant 消息原样带上。只发结果不发申请，模型会看到一个来路不明的 tool 消息。

为什么是这样设计的

这套协议的核心约束是：模型是无状态的。它不记得上一次请求发生过什么，每次你都要把完整历史发过去，它才"看到"了之前的一切。这也是为什么后面阶段 2 要专门讲上下文窗口——历史只会越来越长，而窗口是有限的。你现在写的 messages.push(...)，就是未来那个问题的起点。

一手来源

协议细节以 DeepSeek 官方的 Tool Calls 文档为准 —— 你走的正是这个接口，它比任何二手教程都可信。原始规范见 OpenAI 的 Function calling 指南（提醒：OpenAI 文档主域已从 platform.openai.com 迁到 developers.openai.com，网上带旧域名的链接多数还有效但会重定向）。

保持 src/agent.ts 完全不动（你写好的 calculatorTool 正是我们要用的）。只重写 src/index.ts：

mini-agent/src/index.ts
import { calculatorTool, openai } from './agent'
import type { ChatCompletionMessageParam } from 'openai/resources/chat/completions'

// 本地真正执行工具的代码。模型只会「填申请表」，干活的是这里。
function runCalculator(args: { operation: string; a: number; b: number }): number {
  switch (args.operation) {
    case 'add':      return args.a + args.b
    case 'subtract': return args.a - args.b
    case 'multiply': return args.a * args.b
    case 'divide':
      if (args.b === 0) throw new Error('除数不能为 0')
      return args.a / args.b
    default:
      throw new Error(`未知操作：${args.operation}`)
  }
}

async function main() {
  // 整个对话历史。模型是无状态的 —— 每次请求都得把这份完整历史发给它。
  const messages: ChatCompletionMessageParam[] = [
    { role: 'user', content: '请计算 5 + 3 的结果' },
  ]

  // ── 请求 1：模型看到工具清单，决定要不要用 ─────────────────
  const round1 = await openai.chat.completions.create({
    model: 'deepseek-flash',
    messages,
    tools: [calculatorTool],
    tool_choice: 'auto',
  })

  const assistant = round1.choices[0].message
  console.log('第一轮 content   =', JSON.stringify(assistant.content))
  console.log('第一轮 tool_calls =', JSON.stringify(assistant.tool_calls, null, 2))

  // 把模型的这条回复原样并入历史 —— 少了这一步，后面的 tool 消息就成了"孤儿"
  messages.push(assistant)

  // ── 本地执行模型"申请"的每一次工具调用 ───────────────────
  for (const call of assistant.tool_calls ?? []) {
    if (call.type !== 'function') continue   // 联合类型必须收窄（见第 6 节）

    const args = JSON.parse(call.function.arguments)  // arguments 是 JSON 文本，不是对象
    const result = runCalculator(args)

    messages.push({
      role: 'tool',
      tool_call_id: call.id,        // 靠它把结果和请求配对
      content: String(result),  // content 必须是字符串
    })
  }

  // ── 请求 2：模型看到结果，给出自然语言回答 ────────────────
  const round2 = await openai.chat.completions.create({
    model: 'deepseek-flash',
    messages,
    tools: [calculatorTool],
    tool_choice: 'auto',
  })

  console.log('最终回答：', round2.choices[0].message.content)
}

main().catch(console.error)

5检查理解

合上代码，凭记忆回答。答错比答对更有价值——错误正好标出了还没长牢的地方。

检查 1 / 3 你拿到 tool_calls[0].function.arguments 时，它是什么？

模型输出的 JSON 里，arguments 是被转义过的文本，不是嵌套对象。用法永远是 JSON.parse(call.function.arguments)。而且模型不保证生成合法 JSON，所以真实项目里这个 parse 必须包在 try/catch 里——这正是阶段 2 要补的错误处理。

检查 2 / 3 工具结果消息里，必须带上什么，模型才能认出这是对哪次调用的回答？

就是 tool_call_id。模型可以在一次回复里发出多个 tool call（并行调用），所以必须靠唯一 ID 配对，而不是工具名。少了它或写错它，API 会直接拒绝这次请求。

检查 3 / 3 第二次请求的 messages 数组，顺序应该是？

历史必须按真实发生的时间顺序排列：先有你的问题，模型才提出申请，你才有结果。这也是为什么代码里用 messages.push(...) 追加，而不是到处 unshift。

6踩坑预警：TypeScript 的联合类型

如果你把第 4 节代码里的 if (call.type !== 'function') continue 删掉，tsc 会报这个错：

tsc 报错（真实复现过）
error TS2339: Property 'function' does not exist on type 'ChatCompletionMessageToolCall'.
  Property 'function' does not exist on type 'ChatCompletionMessageCustomToolCall'.

原因：SDK 里 ChatCompletionMessageToolCall 其实是一个联合类型——Function 型（有 function 字段）和 Custom 型（有 custom 字段）。你只定义了 function 型工具，所以要用 if (call.type !== 'function') continue 把类型"收窄"到那一支。↗

这不是障碍，是提醒：模型可以调用的东西不止一种，你的执行器必须按类型分派。等工具多起来，这个 switch 会长成一个注册表——那正是 Pi 这类项目里"工具系统"的雏形。

7另一个坑：thinking 模式要求回传 reasoning_content

这个坑不属于 TypeScript，属于 DeepSeek 协议本身，而且直接关系到你当前的代码。

你原来的请求里写着 reasoning_effort: 'high' —— 这是合法参数，会让模型进入 thinking（思考）模式。而官方文档规定：

DeepSeek 官方规则

thinking 模式下，一旦发生过工具调用，之前每一轮的 reasoning_content 都必须在后续请求中完整回传，否则请求被拒（HTTP 400，大意是「reasoning_content 必须传回」）。而且空字符串 "" 也不能丢。

出处：DeepSeek — Thinking 模式下的 tool call 示例。

这条规则的杀伤力在于它的持续性：很多客户端重放历史时，习惯只挑 role、content、tool_calls 三个字段重新拼一个对象。这么一拼 reasoning_content 就丢了，而这条被污染的消息会在之后每一次请求里被重放，于是整个会话持续 400，只能推倒重来。genkit、n8n、乃至 DeepSeek 自己的 harness 都在这里翻过车。

你的代码为什么天然避开了这个坑

因为我们 push 的是模型返回的整个 message 对象：

messages.push(assistant)   // ✅ 整个对象，reasoning_content 等一切字段原样带上

而不是手工重建：

messages.push({
  role: 'assistant',
  content: assistant.content,
  tool_calls: assistant.tool_calls,   // ❌ 悄无声息地丢掉了 reasoning_content
})

这不是运气，正是第 ③ 条「历史要完整」的具体后果：永远不要手工挑字段重建 assistant 消息。这个小习惯以后会替你省掉一整类极难排查的 bug。

诚实说明

reasoning_effort: 'high' 是否真的让 deepseek-flash 进入 thinking 模式、从而是否触发这条规则，我没有实测过（实测要动用你的 API key）。所以：第一次运行如果报 400 且提到 reasoning_content，就是这条，告诉我我们一起处理；如果顺利跑通，说明这次没走 thinking 路径，这条规则暂时不影响你——但以后想开 thinking 时它一定会回来。

8验证你的理解：三个破坏性实验

能跑通不代表理解。真正把理解钉牢的办法是故意弄坏它，然后预测会发生什么、再验证。每个实验只改一行，改完记得改回来。

  • 实验 A：把 messages.push(assistant) 注释掉。先写下你预测的报错，再运行。
    它在验证：模型认的是消息历史，不是你的意图。
  • 实验 B：把 tool_call_id: call.id 改成 tool_call_id: 'abc'。同样先预测再运行。
    它在验证：配对是按 ID 严格做的。
  • 实验 C：把请求里的用户消息改成 '请计算 5 除以 0'，观察 runCalculator 抛出的异常怎么结束程序。
    它在验证：工具抛错时，agent 目前直接崩了。这正是阶段 2 "错误处理"要解决的问题。
把结果记下来

按你自己 ROADMAP 里的模板，把三个实验的实际报错和你的预测差异写进 notes/。预测和实际不一致的地方，就是你下一个要搞懂的机制。

9下一步

你现在有了四条消息的全貌，也知道了"再来一轮"该怎么做。第 2 课的主题是把这两次请求折成循环，并第一次认真处理"什么时候停"——因为一旦有了循环，模型可以连续调工具，你需要一道刹车。

那节课之后你就会发现：今天这四行 messages.push 会长成整个 agent 的骨架。
